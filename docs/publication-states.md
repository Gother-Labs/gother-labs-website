# Publication States And Release Authority

This repository is a static GitHub Pages site. A file being present in a branch, generated by a tool, or visible in a pull-request diff does **not** by itself make that file an approved or live Göther Labs publication.

This document defines the minimum release-state model for the website without adding a framework, CMS, preview service, or parallel approval system.

## The decisive rule

For public authority, use this chain:

`source / edit → reviewed PR → required site-integrity PASS → merge to main → Pages verify PASS → Pages deploy PASS`

Only the final state is production.

The exact production identity is therefore a pair:

- the merged website `main` commit SHA;
- the successful GitHub Pages deployment run for that SHA.

A newer local checkout, branch, generated file, or successful PR check must never be described as production until that chain completes.

## State model

The words below describe different aspects of publication and are not all mutually exclusive. In particular, `generated` describes provenance, while `experimental` describes public authority/indexability.

### Production / live

A route or artifact is **production** only when all of the following are true:

1. its exact bytes are contained in the explicit `_site` Pages artifact built from merged `main`;
2. the reusable `site-integrity` verification succeeds for that merged SHA;
3. the GitHub Pages `deploy` job succeeds for the same SHA.

Production does not mean that every production route is a canonical publication. A deliberately `noindex` experimental or historical route can be live while remaining non-canonical.

### Approved / release candidate

A change is **approved for release** when it is represented by a reviewable pull request and the required `site-integrity` check passes on its exact head SHA.

This means the change is eligible to merge. It is not yet live and must not be presented as production evidence.

Approval evidence should contain, at minimum:

- issue or stated scope;
- exact PR head SHA;
- required CI result;
- reviewed generated/content/visual diffs where applicable.

### Generated

A page or artifact is **generated** when its website representation is reproducibly derived by the versioned website tooling from declared source inputs.

For Results, the authoritative source input is the sibling `Gother-Labs/gother-labs-results` repository at the exact commit recorded in `tools/generated-results.lock.json`. A moving branch tip is not an admissible release identity.

The website repository contains the release projection of that source. `tools/sync-results.mjs --check`, provenance checks, declared-artifact checks, the generated-content shape contract, and browser/visual checks collectively protect that projection.

Generated does **not** imply approved or production. Generated output on a local checkout or feature branch remains unpublished until it passes the normal PR/merge/deploy chain.

Some rich Result detail pages and retained run surfaces are explicitly curated website-owned publication boundaries recorded by the generated-results lock. That designation prevents silent overwrite; it does not exempt them from release checks.

### Experimental / noindex

An **experimental** public route is intentionally accessible but is not a canonical indexed publication or commercial/evidence entry point.

Current documented noindex surfaces include:

- `/evolther/`;
- retained historical `results/*/run/` routes;
- the custom 404 surface.

These routes must preserve the documented `noindex` policy and must not be used to imply a stronger publication status than their role allows. Historical run routes are archives; canonical Result pages remain the public evidence entry points.

An experiment can therefore be both `production/live` and `experimental/noindex`: the first says its bytes were deployed, the second says how much public authority/indexability the route carries.

### Local / branch-only / unpublished

Any change that exists only in a local workspace, generated temporary tree, feature branch, unmerged PR, or failed deployment is **unpublished**.

Unpublished material may be used for review and testing. It must not be described as current website state, approved evidence, or production behavior.

## Source authority

### Hand-authored website surfaces

For hand-authored pages such as Home, Company, Contact, and the RTL/PPA pilot, the website repository is the publication source. The authoritative public version is the exact version from the successfully deployed `main` SHA.

### Results and evidence artifacts

For generated Result metadata, articles, and declared evidence artifacts, source authority lives in the pinned `Gother-Labs/gother-labs-results` commit named by `tools/generated-results.lock.json`.

The website generator owns the transformation into public HTML and copied public artifacts. The website release is authoritative for presentation; the pinned Results source remains authoritative for source evidence/provenance.

### Curated publication surfaces

Website-owned curated Result detail pages, retained historical run surfaces, and curated support paths are explicitly enumerated in the lock. They remain subject to generated-source provenance, content-integrity, link/HTML, visual/browser, and claim-boundary checks as applicable.

## Required evidence before merge

The required `site-integrity` job is the release gate. It currently checks, among other things:

- pinned Results source provenance;
- release-quality unit tests;
- Result Markdown contract;
- shared site shell;
- exact `_site` Pages artifact construction;
- links, metadata, sitemap, robots/indexability, HTML and metric claims;
- generated Result content shape;
- bounded RTL claims;
- generated Result/artifact byte alignment;
- browser/visual regression coverage and critical interactions;
- patch whitespace.

A failing required check means the candidate is not approved for release.

Intentional generated-content or visual changes must be reviewed before updating their committed contracts/baselines. Regenerating a contract or screenshot merely to silence CI is not approval.

## Required evidence after merge

A merge is not the final production assertion. After a material website release, verify the GitHub Pages workflow for the merged SHA and record:

- merged `main@<SHA>`;
- Pages workflow run ID;
- `verify / site-integrity = PASS`;
- `deploy = PASS`.

For changes to customer-visible behavior, a targeted live-route check may be added when it materially improves confidence, but it does not replace the Pages run identity.

Issue/PR closure may be automatic on merge. When production verification is material to the workstream, append the deployment evidence to the issue after the Pages run completes.

## Decision table

| Situation | Generated? | Approved? | Live? | Canonical/indexable? |
| --- | --- | --- | --- | --- |
| Local regenerated Result before PR | Yes | No | No | No |
| PR with passing required CI | Maybe | Yes for release | No | No production claim yet |
| Merged `main`, Pages deploy still running | Maybe | Yes | Not yet verified | Do not claim production yet |
| Successful Pages deployment of canonical page | Maybe | Yes | Yes | According to page robots/canonical policy |
| Successful Pages deployment of `/evolther/` | No/route-specific | Yes | Yes | No — experimental/noindex |
| Successful Pages deployment of retained `results/*/run/` | Curated/archive | Yes | Yes | No — historical/noindex |

## Contributor workflow

Before opening a PR, follow the validation commands in `README.md` and `docs/preview-qa.md`.

Before calling a change production, verify the merged SHA in the Pages workflow. When answering questions about what the public site currently says or does, prefer the latest successfully deployed `main` SHA over a local workspace or open PR.

This release-state model deliberately stays small: Git, the required CI gate, the explicit Pages artifact, and the Pages deployment run are the system of record.
